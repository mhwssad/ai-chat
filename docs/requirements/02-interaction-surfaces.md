# 交互入口需求

## 1. 目标

系统应通过 `Web / TUI / API` 三个正式入口向用户暴露能力，并共享同一套核心服务、配置来源、状态语义和错误语义。

交互入口不应各自复制聊天、模型、工具、记忆或 Agent 逻辑。

## 2. 范围与边界

### 2.1 Web

Web 是面向日常使用和可视化操作的主要交互面。

### 2.2 TUI

TUI 是面向开发者和高级用户的终端工作台。业务型命令行交互应收敛到 TUI，而不是保留独立业务 CLI 子命令。

### 2.3 API

API 是供前端界面、自动化流程和外部集成使用的共享服务入口。

### 2.4 命令入口边界

`main.py` 对外命令应只保留：

1. `serve`
2. `tui`

系统不再把独立业务 CLI 视为正式产品入口。

## 3. Web 需求

系统应满足以下 Web 要求：

1. Web 应支持会话创建、消息发送、流式输出和历史查看。
2. Web 应支持模型选择和会话内模型切换。
3. Web 应支持查看基础工具状态、记忆状态和错误信息。
4. Web 应通过 API 访问核心服务，而不是在前端层复制业务逻辑。
5. Web 应为 Agent、RAG、媒体和配置能力提供可扩展入口。

## 4. TUI 需求

系统应满足以下 TUI 要求：

1. TUI 应作为统一业务控制台承接终端侧业务交互。
2. TUI 应覆盖对话、Agent、工具、记忆、调度、RAG、统计、图像、语音和系统动作。
3. TUI 应提供工作台式布局，并支持不同终端宽度下的可用性。
4. TUI 应通过 DI 注入共享服务，不应在面板内部直接导入全局容器获取依赖。
5. TUI 应统一使用共享状态、输入、确认和反馈机制。

## 5. API 需求

系统应满足以下 API 要求：

1. API 应提供聊天、Agent、会话、模型、工具、记忆、RAG、调度、媒体和技能相关接口。
2. API 应复用共享服务层，而不是维护第二套服务实现。
3. API 应返回结构化错误，便于 Web 和自动化流程统一处理。
4. API 应暴露可验证的健康检查和运行态接口。

## 6. 共享行为要求

三个入口应共享以下行为：

1. 同一份模型与配置数据。
2. 同一份会话与消息状态。
3. 同一份工具启用状态与权限语义。
4. 同一份记忆与 RAG 服务边界。
5. 同一份审计与错误分类规则。

## 7. 错误与状态反馈要求

系统应满足以下要求：

1. Web、TUI 和 API 对同一错误源应给出一致判断。
2. 用户应能区分配置错误、模型错误、工具错误、存储错误和运行时错误。
3. 长任务、流式输出和 Agent 执行应具有明确状态，不应只依赖临时提示信息。

## 8. 交互一致性要求

系统应保持以下一致性：

1. 模型切换规则在 Web、TUI 和 API 中一致。
2. 会话与消息生命周期在各入口中一致。
3. 工具、记忆和 RAG 的数据来源一致。

## 9. 验收标准

1. Web、TUI 和 API 都可以访问共享核心能力。
2. `main.py` 的正式入口只保留 `serve` 与 `tui`。
3. 不再存在对外暴露的独立业务 CLI 子命令体系。
4. 三个入口对同类错误给出一致解释。
