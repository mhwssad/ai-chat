# 数据模型需求

## 1. 目标

系统应定义一套可迁移、可审计、可扩展的数据模型，用于支撑业务配置、会话运行态、调用记录、记忆与任务系统。

## 2. 范围与边界

本文件定义逻辑数据模型与实体边界，不替代 `docs/data.sql` 作为具体 schema 参考。

`docs/data.sql` 应作为当前 schema 的主要技术参考，而本文件定义产品与系统层面的数据实体要求。

## 3. 设计原则

系统数据模型应遵循以下原则：

1. 配置类实体与运行态实体分离。
2. 状态字段可解释。
3. 错误与审计字段可追踪。
4. 敏感信息默认脱敏或加密。
5. schema 演进可控。

## 4. 核心实体总览

系统应至少包含以下实体类别：

1. 配置类实体。
2. 会话与消息实体。
3. 模型与工具调用实体。
4. 权限与审计实体。
5. 记忆与 RAG 实体。
6. 调度与任务相关实体。

## 5. 配置类实体

配置类实体应覆盖：

1. Providers
2. Models
3. App Settings
4. MCP Servers
5. Skills
6. Security Policies
7. Prompt Templates

这些实体应支持启用状态、更新时间和扩展元数据。

## 6. 会话与消息实体

系统应支持以下会话与消息实体能力：

1. Session 记录标题、当前模型、状态、消息计数和时间信息。
2. Message 记录角色、内容、状态、错误信息和必要模型信息。
3. 会话与消息应支持历史重载和错误状态持久化。

## 7. 调用实体

系统应支持以下调用类实体：

1. Model Calls
2. Tool Calls
3. Permission Decisions
4. Audit Logs

这些实体应支持：

1. 时间记录。
2. 状态记录。
3. 输入摘要。
4. 输出摘要。
5. 错误分类。
6. 扩展 metadata。

## 8. 记忆与 RAG 实体

系统应支持记录：

1. Memory Entries
2. Summaries
3. 知识索引边界与文档元信息
4. 会话级与全局级作用域标记

并为长期记忆和更复杂 RAG 元数据保留可扩展空间。

## 9. 调度与任务实体

系统应支持：

1. Scheduled Tasks
2. Task Execution Logs
3. 与 Agent Runtime 相关的后续状态演进空间

当前阶段若 Agent 恢复状态尚未完全入库，数据模型也应为后续扩展保留清晰边界。

## 10. schema 演进规则

数据模型演进应满足以下要求：

1. 新字段增加不应破坏已有会话与历史记录。
2. 状态枚举变化应有迁移边界。
3. 持久化结构应允许未来扩展更多工具来源、任务状态和能力元数据。

## 11. 与 `docs/data.sql` 的关系

`docs/data.sql` 是当前 SQLite schema 的技术基线。

本文件定义的实体、职责与边界应与 `docs/data.sql` 保持方向一致；若两者冲突，应通过 schema 更新和需求文档同步来修正，而不是长期并存双重事实来源。

## 12. 验收标准

1. 数据模型能够覆盖配置、会话、调用、审计、记忆和任务主要场景。
2. 敏感字段具备明确保护策略。
3. schema 具备可迁移与可扩展边界。
4. 需求文档与 `docs/data.sql` 在实体方向上保持一致。
