# Chat And Models Requirements

## 1. 目标

聊天与模型模块是第一阶段的核心体验。它应提供稳定的 Web 聊天、CLI 请求、多供应商模型调用、模型切换、流式输出、会话历史和清晰错误处理。

该模块不应直接耦合具体供应商实现，而应通过统一模型接口访问不同供应商和模型。

## 2. 聊天需求

### 2.1 会话

系统应支持创建会话、查看会话列表、打开历史会话、继续已有会话和保存会话标题。

每个会话应记录当前默认模型、消息数量、创建时间、更新时间和最近错误状态。

### 2.2 消息

消息应至少支持用户消息、助手消息、系统消息和工具结果消息。

每条消息应记录角色、内容、所属会话、使用模型、创建时间、状态和错误信息。

### 2.3 流式输出

聊天回复应优先支持流式输出。Web 界面应边接收边展示，CLI 可选择流式打印或等待完整结果。

流式输出过程中应支持错误终止，并保留已经生成的部分内容和错误状态。

### 2.4 上下文组装

系统应根据当前会话消息、系统提示、会话内记忆、工具结果摘要和模型限制组装请求上下文。

上下文组装应独立于 Web 和 CLI，以便两个入口得到一致行为。

### 2.5 中断与取消

MVP 应为取消请求预留接口。Web 可提供停止生成按钮，CLI 可响应终端中断。

第一阶段不要求跨进程恢复被取消的请求。

## 3. 模型供应商需求

### 3.1 供应商配置

供应商配置应来自配置文件。配置内容应包含供应商标识、显示名称、基础 URL、API Key 环境变量名、默认模型、可用模型列表和启用状态。

配置文件不应保存明文 API Key。

### 3.2 模型信息

模型信息应包含模型标识、显示名称、所属供应商、能力标签、是否支持流式输出、是否支持工具调用、上下文长度和启用状态。

能力标签可包括 chat、tools、vision、embedding、reasoning 等。

### 3.3 模型切换

用户应能在新建会话时选择模型，也应能在已有会话中切换模型。

模型切换应影响后续消息，不应重写历史消息的模型记录。

### 3.4 默认模型

系统应支持全局默认模型。若会话未指定模型，应使用全局默认模型。

如果默认模型不可用，系统应给出明确错误，并建议用户检查配置。

## 4. 错误处理

### 4.1 配置错误

配置缺失、格式错误、API Key 环境变量不存在、模型不存在时，系统应指出具体配置项。

### 4.2 调用错误

供应商网络错误、认证失败、限流、模型不可用、响应格式异常时，系统应转化为统一错误结构。

错误结构应包含错误类型、用户可读消息、技术细节、是否可重试和来源供应商。

### 4.3 部分结果

流式响应中断时，系统应保存已生成内容，并标记消息为部分完成或失败。

## 5. Web 行为

- 聊天页面应显示当前模型。
- 用户应能切换模型。
- 流式输出应实时追加。
- 错误应显示为可理解提示。
- 历史会话应可继续。
- 高级信息应可折叠展示，例如供应商、耗时、错误细节。

## 6. CLI 行为

- CLI 应支持一次性聊天请求。
- CLI 应支持指定模型。
- CLI 应支持查看供应商和模型列表。
- CLI 应支持检查配置。
- CLI 错误输出应适合开发者排查。

## 7. 验收标准

- 至少两个供应商或两个模型可以通过同一接口调用。
- Web 可以创建会话并流式接收回复。
- CLI 可以发起一次请求并输出结果。
- 模型切换只影响后续消息。
- 配置错误和供应商错误可以被清晰区分。
- 历史消息保存后可重新加载。
