# 范围与路线图

## 1. 目标

本文件定义项目范围管理方式，以及 `MVP / 近期 / 远期` 的阶段目标。系统应通过明确的阶段边界控制复杂度，避免在同一阶段同时追求完整工作台、完整 Agent 平台和完整工程治理能力。

## 2. 范围管理原则

系统范围管理应遵循以下原则：

1. 先交付可独立使用的工作台底座，再逐步增强 Agent Runtime。
2. 先统一能力边界，再增强高级体验。
3. 先保证共享核心一致性，再扩展多个交互入口。
4. 阶段目标必须可验证，而不是只保留概念性愿景。

## 3. MVP 范围

MVP 阶段系统应至少包含以下能力：

1. Web 聊天主流程。
2. TUI 工作台主流程。
3. API 形式的聊天、会话、工具、记忆、RAG、Agent 和媒体入口。
4. 多模型供应商配置与模型切换。
5. 会话与消息持久化。
6. 统一 ChatService 和共享服务层。
7. 统一 Tool Registry 的最小可用实现。
8. 会话内记忆与基础 RAG 能力。
9. 基础 Agent 执行链路和最小可观察性。
10. SQLite 配置、运行态数据和基础审计记录。

## 4. 近期目标

近期阶段系统应增强以下能力：

1. 完整 TUI 工作台体验，包括更清晰的执行状态、检视区和系统状态展示。
2. Tool Registry 的权限策略、启用禁用、诊断和可视化状态。
3. MCP servers 的连接检查、工具发现、状态展示和调用日志。
4. Skills 的发现、状态管理和能力说明。
5. Agent 调试视图、执行轨迹、失败步骤和取消机制。
6. RAG 索引管理、会话级作用域、上下文构建和文档操作体验。
7. 更稳定的配置校验、运行态审计和错误分类。

## 5. 远期目标

远期阶段系统应演进到以下能力：

1. 后台任务队列和长任务状态管理。
2. Agent 任务恢复、断点续跑和更细粒度状态机。
3. 长期记忆与可解释的跨会话上下文。
4. 更强的项目知识库、代码索引和复杂检索策略。
5. 更严格的工具隔离、确认流程和可选执行沙箱。
6. 更完整的工程师模式与运行态观察面板。

## 6. 非目标

下列内容不属于当前路线图的强制目标：

1. 团队协作、多用户权限和组织级管理。
2. 云端同步和托管式多端共享。
3. 独立业务 CLI 子命令体系。
4. 脱离共享核心的第二套聊天或 Agent 执行逻辑。

## 7. 优先级规则

优先级判断应遵循以下顺序：

1. 共享核心一致性优先于单一入口体验优化。
2. 状态、错误、权限和审计一致性优先于新功能扩展。
3. Web、TUI 和 API 的主流程可用性优先于高级实验功能。
4. Agent 运行时增强应复用现有核心边界，而不是复制实现。

## 8. 风险与依赖

主要风险包括：

1. 如果同时扩张聊天、工具、MCP、记忆、RAG 和 Agent 深度，范围会失控。
2. 如果 Web、TUI 和 API 各自实现核心逻辑，行为会迅速分叉。
3. 如果路线图分散在各主题文档中维护，阶段口径会失真。

主要依赖包括：

1. 稳定的模型配置与调用抽象。
2. 可复用的 Tool Registry 和 ContextService。
3. 可迁移的 SQLite schema 与审计边界。

## 9. 阶段验收方向

### 9.1 MVP 验收方向

1. 用户可以通过 Web 完成主要聊天流程。
2. 用户可以通过 TUI 完成主要业务工作台操作。
3. API 可提供与界面一致的核心服务能力。
4. 模型、工具、记忆和会话状态有统一数据来源。

### 9.2 近期阶段验收方向

1. Agent 执行可以观察、取消并查看错误链路。
2. MCP、Skills 和 Tool Registry 的状态更加清晰可管理。
3. RAG 与记忆操作具备更稳定的工作流体验。

### 9.3 远期阶段验收方向

1. Agent Runtime 可承载长任务和更复杂编排。
2. 长期记忆、项目知识和安全隔离形成完整体系。
