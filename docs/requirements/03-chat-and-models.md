# 聊天与模型需求

## 1. 目标

系统应提供稳定、一致、可扩展的聊天与模型能力，使 Web、TUI 和 API 能够围绕统一会话、统一模型抽象和统一上下文组装逻辑完成交互。

## 2. 范围与边界

聊天与模型模块负责：

1. 会话与消息生命周期。
2. 聊天主流程。
3. 模型供应商与模型配置。
4. 模型切换与默认模型。
5. 流式与非流式输出。
6. 上下文组装和工具调用循环。

该模块不直接负责：

1. 复杂 Agent 多步骤编排。
2. 工具权限策略决策本身。
3. 长期记忆产品策略。

## 3. 会话需求

系统应支持：

1. 创建会话。
2. 列出会话。
3. 打开历史会话。
4. 继续已有会话。
5. 记录会话标题、当前模型、消息数量、创建时间和更新时间。

系统应允许会话保存最近一次错误状态和必要的扩展元数据。

## 4. 消息需求

系统应至少支持以下消息角色：

1. `human`
2. `ai`
3. `system`
4. `tool`

消息应记录内容、角色、关联会话、创建时间、状态、错误信息和必要的模型信息。

## 5. 聊天主流程

系统应通过统一聊天服务完成以下流程：

1. 接收用户输入。
2. 组装上下文。
3. 获取目标模型实例。
4. 绑定可用工具。
5. 调用模型并执行工具调用循环。
6. 保存会话与消息历史。
7. 在需要时执行记忆提取。

## 6. 流式输出

系统应优先支持流式输出。

1. Web 应边接收边展示输出。
2. API 应能提供事件流或可等价消费的流式结果。
3. 流式过程中发生错误时，系统应保留已生成内容并标记状态。

## 7. 模型供应商与模型配置

系统应支持：

1. 多供应商配置。
2. 多模型配置。
3. 默认模型设置。
4. 模型启用与禁用。
5. 模型能力标签描述。
6. API Key 加密保存。

SQLite 应作为模型与供应商配置的主要持久化来源。

## 8. 模型切换

系统应允许用户在会话建立前或会话进行中切换模型。

模型切换应只影响后续消息，不应回写历史消息的模型记录。

## 9. 上下文组装

系统应根据以下来源组装上下文：

1. 会话消息历史。
2. 系统提示。
3. 会话内记忆。
4. 工具结果摘要。
5. RAG 检索结果。
6. 模型限制。

上下文组装应独立于 Web、TUI 和 API，保证行为一致。

## 10. 错误处理

系统应对以下错误进行统一处理：

1. 配置错误。
2. 模型不可用。
3. 供应商认证失败。
4. 网络错误与超时。
5. 工具调用链错误。
6. 流式中断错误。

错误结构应至少包含：

1. 错误类型。
2. 用户可读消息。
3. 技术细节。
4. 是否可重试。
5. 来源模块或供应商。

## 11. 约束与风险

1. 聊天主流程不应绑定单一模型供应商实现。
2. 上下文组装不应在不同入口中重复实现。
3. 模型切换、流式输出和工具循环必须共享同一服务边界。

## 12. 验收标准

1. 至少支持多个模型或多个供应商通过同一接口调用。
2. Web、TUI 和 API 对同一会话使用一致的消息与模型规则。
3. 模型切换只影响后续消息。
4. 流式输出可被中断并保留部分结果状态。
