# MVP Scope Requirements

## 1. 目标

第一阶段目标是交付一个可靠的本地 AI 工作台底座，让用户可以通过 Web 完成主要聊天流程，通过 CLI 完成基础调用和诊断，并为后续 Agent、工具、MCP、skills 和记忆能力留下清晰扩展边界。

MVP 不追求完整 Agent 平台，而是优先保证聊天、模型、会话、配置、存储和基础能力注册稳定可用。

## 2. 核心原则

- MVP 必须能独立使用，而不是只作为未来系统的半成品。
- 所有核心模块应通过异步接口组织。
- Web 与 CLI 应共享同一套核心服务，不应各自实现聊天和模型调用逻辑。
- 配置文件是系统显式配置的真实来源。
- SQLite 是运行态数据的主要存储。
- 工具、MCP、skills 在 MVP 中先统一边界，不要求完整高级管理体验。

## 3. MVP 必做范围

### 3.1 Web 聊天主流程

用户应能在 Web 界面中创建会话、发送消息、接收模型回复、查看历史消息，并在模型回复过程中看到流式输出。

### 3.2 CLI 最小入口

用户应能通过 CLI 启动服务、发起一次性聊天请求、查看供应商状态、查看模型列表、检查配置有效性。

### 3.3 多供应商与模型切换

系统应从配置文件读取供应商和模型配置，并允许用户在聊天前或聊天过程中选择模型。

### 3.4 会话和消息持久化

系统应保存会话、消息、模型选择、创建时间、更新时间和基础错误状态。

### 3.5 统一工具注册表

系统应提供统一工具注册表的最小实现，用于注册、列出、启用、禁用和描述工具能力。

### 3.6 会话内记忆

系统应支持当前会话内的上下文组织，包括消息历史、模型选择、工具调用摘要和必要的系统状态。

### 3.7 基础权限与审计

工具能力应声明权限需求。系统应记录模型调用、工具调用、权限决策和错误信息。

## 4. MVP 非目标

第一阶段不要求实现以下能力：

- 多用户账号系统。
- 团队权限和共享空间。
- 云端同步。
- Web 直接编辑供应商配置。
- 完整 MCP server 管理面板。
- 完整 skills 安装与市场机制。
- 自动长期记忆提取。
- 项目知识库索引。
- 后台任务队列。
- 长任务暂停、恢复和跨进程续跑。
- 完整沙箱执行环境。

## 5. 验收标准

- 用户可以在 Web 中完成一次完整聊天，并看到流式回复。
- 用户可以切换至少两个已配置模型。
- 用户可以通过 CLI 查看模型列表并发起一次请求。
- 会话刷新后仍可查看历史消息。
- 模型调用失败时，界面和 CLI 都能给出清晰错误。
- 工具注册表可以列出工具及其权限声明。
- 审计日志可以记录一次模型调用和一次工具调用的基础信息。
- 配置中缺少 API Key 或模型不可用时，系统能明确指出问题来源。

## 6. 优先级

### 6.1 P0

- Web 聊天。
- 模型调用接口。
- 配置读取。
- 模型列表。
- 会话和消息存储。
- 流式输出。
- CLI 基础诊断。

### 6.2 P1

- 聊天中模型切换。
- 工具注册表最小实现。
- 基础权限声明。
- 调用日志。
- 会话内记忆。

### 6.3 P2

- 供应商状态页面。
- 工具状态页面。
- 更完整 CLI 子命令。
- 高级错误诊断。
- Agent 实验室入口占位。

## 7. 风险与约束

- 如果 MVP 同时追求完整工具链、长期记忆和 Agent 编排，范围会失控。
- 如果 Web 和 CLI 不共享核心服务，后续会出现重复逻辑和行为不一致。
- 如果配置和运行态数据不分离，模型管理、会话历史和审计日志会难以维护。
- 如果权限和审计不在 MVP 阶段建立边界，后续工具、MCP、skills 的风险会快速放大。
