# AI Workbench Requirements

## 1. 产品定位

本项目定位为个人/开发者本地 AI 工作台，同时也是 Agent 开发框架与 UI 壳。

它不是单纯的聊天页面，也不是只面向终端的脚本工具。它应当提供一个稳定、可扩展、可观察的 AI 能力运行环境，让开发者可以在 Web 或 CLI 中使用多供应商模型、切换模型、管理工具能力、接入 MCP 与 skills，并逐步构建具备记忆和任务执行能力的 Agent 系统。

第一阶段应优先解决“可靠、清晰、可继续扩展”的问题，避免在聊天、工具、记忆、MCP、skills、Web、CLI 之间分散实现。

## 2. 产品原则

### 2.1 本地优先

项目默认面向个人和开发者本地使用。配置、会话、记忆、工具状态等数据应优先保存在本地，用户应能理解数据存放位置和用途。

### 2.2 异步优先

核心接口应采用异步设计。模型调用、聊天流式输出、工具执行、MCP 通信、记忆读写、Web 请求处理等能力应尽量通过 async/await 组织。

第一阶段不要求完整后台任务队列和长任务恢复，但接口边界应为后续并发编排、任务取消、重试和恢复留出空间。

### 2.3 配置透明

供应商、模型、默认模型、API Key 环境变量名等基础配置应以配置文件作为 source of truth。Web 和 CLI 第一阶段主要负责查看、验证、启用和禁用，不强制要求直接写回配置。

### 2.4 能力统一

系统最终应通过统一工具注册表向 Agent 暴露可调用能力。普通工具、MCP server 提供的工具、skills 提供的能力，都应进入统一注册表，供聊天和 Agent 流程按权限策略调用。

### 2.5 渐进披露

默认体验应接近轻量 AI 工作台，保证聊天、模型切换和历史记录简单可用。高级能力应以工程师模式或 Agent 实验室方式逐步展开，包括工具列表、MCP 状态、skills、记忆、执行轨迹、日志和调试信息。

### 2.6 可审计与可关闭

工具执行、MCP 调用、skills 调用、记忆写入等行为应可观察、可审计，并允许用户关闭或限制。系统不应默认进行不可见、不可解释的高风险行为。

## 3. 目标用户与核心场景

### 3.1 目标用户

主要用户是本地开发者、AI 工具使用者、Agent 能力实验者，以及希望把多个模型供应商、工具系统和本地知识能力整合到一个工作台中的个人用户。

### 3.2 核心场景

- 用户在 Web 界面中进行日常聊天，并可在聊天过程中切换模型。
- 用户通过 CLI 快速发起一次性请求、调试模型连接、检查工具和供应商状态。
- 用户通过配置文件接入多个模型供应商，并在 Web/CLI 中验证可用性。
- 用户在聊天或 Agent 流程中调用工具能力，包括本地工具、MCP 工具和 skills 派生能力。
- 用户查看工具调用过程、结果、错误和权限决策。
- 用户使用会话历史继续上下文，并在后续阶段使用长期记忆和项目知识库。
- 用户以 Agent 实验室方式观察模型推理、工具调用、记忆检索和任务执行轨迹。

## 4. MVP 范围

MVP 的目标是完成一个可靠的本地 AI 工作台底座，而不是一次性完成完整 Agent 平台。

### 4.1 MVP 必须包含

- Web 聊天主流程。
- CLI 最小入口。
- 多供应商配置读取。
- 模型列表展示与聊天时模型切换。
- 会话与消息持久化。
- 聊天流式输出。
- 统一工具注册表的接口定义与最小实现。
- MCP 与 skills 作为工具来源的概念边界。
- 会话内记忆。
- 长期记忆接口预留。
- 基础错误处理与调用日志。
- 基础权限分级模型。
- 配置文件与 SQLite 的混合持久化策略。

### 4.2 MVP 暂不强制包含

- Web 界面直接编辑供应商配置。
- 完整后台任务队列。
- 长任务暂停、恢复和跨进程续跑。
- 自动长期记忆提取。
- 项目代码或文档知识库索引。
- 完整沙箱执行环境。
- 多用户账号、权限和团队协作。
- 云端同步。

## 5. 长期蓝图

长期目标是把项目演进为本地优先的 AI 工作台与 Agent 开发框架。

### 5.1 Agent 编排

支持更复杂的 Agent 执行流程，包括多步骤任务、工具选择、状态追踪、任务取消、重试、恢复和结果总结。

### 5.2 MCP 管理

支持 MCP server 的配置、连接检查、工具发现、启用禁用、调用日志和错误诊断。

### 5.3 Skills 管理

支持 skills 的发现、安装、启用禁用、能力说明、输入输出约束和调用记录。

### 5.4 长期记忆

支持用户偏好、项目背景、常用约定、任务历史等长期记忆。长期记忆必须可查看、可删除、可禁用，并能解释来源。

### 5.5 项目知识库

支持将项目文档、笔记和可选代码内容纳入本地知识检索。知识库应有明确索引范围、更新时间和隐私边界。

### 5.6 高级工程师模式

支持更完整的调试视图，包括模型请求、工具调用、MCP 连接、skills 执行、记忆命中、token 使用、耗时、错误和权限决策。

## 6. 核心模块需求

### 6.1 聊天模块

聊天模块负责会话创建、消息发送、模型响应、流式输出、上下文组装、错误展示和历史查看。

聊天模块不应直接绑定某一个供应商实现，而应通过统一模型调用接口访问模型。

### 6.2 供应商与模型模块

供应商与模型模块负责读取供应商配置、列出可用模型、校验 API Key、提供默认模型，并允许聊天过程中切换模型。

配置文件应作为供应商和模型配置的真实来源。Web/CLI 第一阶段负责查看和验证，后续可扩展为可视化编辑。

### 6.3 工具注册表

工具注册表是 Agent 可调用能力的统一入口。

每个工具应声明名称、说明、输入参数、输出格式、权限需求、来源、启用状态和调用方式。工具来源可以是内置工具、MCP server 或 skills。

### 6.4 MCP 模块

MCP 模块负责读取 MCP server 配置、连接 server、发现工具，并将 MCP 工具注册到统一工具注册表。

MCP 模块第一阶段可以只定义清晰边界和最小连接验证，后续再完善运行态管理和调试视图。

### 6.5 Skills 模块

Skills 模块负责发现可用 skills、读取说明、判断适用场景，并将可调用能力暴露给工具注册表。

Skills 不应绕过工具权限系统直接执行高风险操作。

### 6.6 记忆模块

记忆模块分为会话内记忆、长期用户记忆和项目知识记忆。

MVP 只要求会话内记忆和长期记忆接口预留。长期记忆和项目知识记忆应在后续阶段实现，并必须支持查看、删除、关闭和来源解释。

### 6.7 Web UI

Web UI 是第一阶段主要用户体验入口。

它应优先支持聊天、模型切换、会话历史、供应商状态、基础工具状态和错误展示。高级 Agent 调试信息应通过高级模式逐步展开，而不是挤压默认聊天体验。

### 6.8 CLI

CLI 是开发者入口。

MVP 应支持启动服务、发起一次性聊天请求、查看供应商状态、查看模型列表、检查配置和进行基础诊断。后续可扩展工具管理、MCP 管理、skills 管理和 Agent 任务执行。

### 6.9 异步任务模块

异步任务模块在第一阶段主要体现为异步接口和可取消的执行流程。

后台任务队列、长任务恢复、并发任务编排和任务状态持久化属于后续增强能力。

### 6.10 存储模块

存储模块负责区分配置数据和运行态数据。

配置数据应保存在配置文件中。运行态数据应保存在 SQLite 中，包括会话、消息、记忆索引、工具状态、调用日志和权限决策记录。

### 6.11 安全与审计模块

安全与审计模块负责工具权限分级、执行前策略判断、调用日志记录、错误记录和高风险操作提示。

第一阶段不要求完整沙箱，但必须避免默认无限制执行高风险能力。

## 7. 数据与配置策略

### 7.1 配置文件

配置文件用于保存显式、可读、可版本化的系统配置，包括供应商、模型、默认模型、API Key 环境变量名、MCP server 配置、skills 启用策略和安全策略。

配置文件不应直接保存明文 API Key。API Key 应通过环境变量或本地安全存储引用。

### 7.2 SQLite

SQLite 用于保存运行态数据，包括会话、消息、工具调用日志、模型调用记录、权限决策、记忆索引和系统状态。

SQLite 是本地优先方案，不代表未来不能扩展到其他存储。

### 7.3 数据可迁移

持久化设计应考虑后续迁移。会话、消息、工具调用日志和记忆数据应有清晰 schema，避免依赖不可解释的临时结构。

## 8. 安全与权限

### 8.1 权限分级

工具和能力应声明权限等级。建议至少区分以下权限类型：

- 只读能力。
- 网络访问。
- 文件读取。
- 文件写入。
- 命令执行。
- 外部服务调用。
- 记忆写入。
- 高风险本地操作。

### 8.2 策略结果

权限策略应支持以下结果：

- 允许执行。
- 拒绝执行。
- 执行前询问用户。

### 8.3 审计日志

工具、MCP、skills、记忆写入和高风险操作都应记录调用日志。日志至少包含时间、来源、工具名称、输入摘要、输出摘要、权限决策、耗时和错误信息。

### 8.4 用户控制

用户应能关闭工具调用、关闭记忆写入、禁用某个 MCP server、禁用某个 skill，并查看最近的能力调用记录。

## 9. 非功能要求

### 9.1 可扩展性

系统应允许新增供应商、新增模型、新增工具来源、新增 MCP server 和新增 skills，而不需要重写聊天主流程。

### 9.2 可测试性

核心模块应可独立测试。模型调用、工具调用、存储、权限策略和记忆模块应能通过 mock 或测试替身验证。

### 9.3 可观察性

系统应记录关键执行路径，包括模型调用、工具调用、MCP 连接、skills 调用、记忆读写、错误和耗时。

### 9.4 错误可恢复

模型调用失败、供应商不可用、工具执行失败、MCP 断开、skills 不可用时，系统应给出清晰错误，并尽量保持当前会话可继续使用。

### 9.5 隐私优先

本地数据默认不上传。涉及项目知识、记忆、工具输入和聊天历史时，应优先考虑本地存储、明确授权和可删除性。

### 9.6 性能目标

聊天主流程应支持流式响应，避免用户等待完整结果后才看到输出。配置读取、模型列表、会话加载和工具状态展示不应明显阻塞 Web 或 CLI 交互。

## 10. 阶段计划

### 10.1 第一阶段：可靠聊天工作台

目标是完成本地 AI 工作台底座。

范围包括 Web 聊天、模型切换、供应商配置读取、CLI 最小入口、会话历史、流式输出、SQLite 运行态存储、统一工具注册表接口、基础权限策略和会话内记忆。

### 10.2 第二阶段：Agent 能力增强

目标是让工具、MCP、skills 和记忆真正进入 Agent 流程。

范围包括 MCP 工具发现、skills 管理、工具调用轨迹、长期记忆、权限询问、高级调试视图和更完整的 CLI 管理能力。

### 10.3 第三阶段：完整本地 AI 工作台

目标是形成可长期使用的开发者 AI 环境。

范围包括项目知识库、后台任务队列、长任务恢复、Agent 编排、可视化配置编辑、运行报告、完整审计和更强的安全隔离。

## 11. 明确不做

第一阶段不做多人账号系统、团队权限、云端同步、计费系统、公开插件市场和完整沙箱环境。

这些能力可能在未来被重新评估，但不应影响当前本地开发者工作台的核心实现。
