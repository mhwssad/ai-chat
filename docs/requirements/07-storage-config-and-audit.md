# 存储、配置与审计需求

## 1. 目标

系统应通过统一存储、统一配置来源和统一审计语义，保证行为可理解、可追踪、可恢复、可迁移。

## 2. 范围与边界

本模块负责：

1. 配置来源策略。
2. SQLite 业务配置与运行态数据边界。
3. API Key 和敏感信息处理。
4. 审计日志与运行记录。
5. schema 演进与备份边界。

## 3. 配置来源策略

系统应采用以下配置来源原则：

1. 启动期配置仅承担最小引导责任。
2. 业务配置应以 SQLite 为主要持久化来源。
3. 供应商、模型、MCP、Skills 和安全策略不应长期依赖散落的配置文件。

## 4. SQLite 角色边界

SQLite 应承担两类职责：

1. 业务配置数据。
2. 运行态数据。

系统应明确区分这两类数据的语义边界，而不是混写为同一种配置状态。

## 5. 业务配置需求

系统应支持保存和管理以下配置：

1. 模型供应商。
2. 模型信息。
3. 默认模型。
4. MCP servers。
5. Skills 状态。
6. 安全策略。
7. 应用级设置。

这些配置应支持读取、写入、校验和后续迁移。

## 6. 运行态数据需求

系统应支持保存以下运行态数据：

1. 会话。
2. 消息。
3. 模型调用记录。
4. 工具调用记录。
5. 审计日志。
6. 记忆与知识索引边界。
7. 调度任务与执行日志。
8. 权限决策记录。

## 7. API Key 与敏感信息处理

系统应满足以下要求：

1. SQLite 不应保存明文 API Key。
2. 外部凭据应加密保存或使用安全引用方式管理。
3. 审计日志不应无条件写入完整敏感输入。
4. 长文本、文件内容和密钥应优先以摘要、脱敏或引用形式记录。

## 8. 审计需求

系统应记录以下关键行为：

1. 模型调用。
2. 工具调用。
3. MCP 调用。
4. Skills 调用。
5. 权限决策。
6. 记忆写入与删除。
7. 关键配置检查。
8. 重要错误。

审计记录应至少包含时间、来源、目标、输入摘要、输出摘要、状态、错误和必要的权限信息。

## 9. 数据迁移与备份

系统应具备以下边界：

1. schema 可演进。
2. 数据可备份。
3. 本地数据可迁移。
4. 持久化结构不依赖不可解释的临时字段组织。

## 10. 约束与风险

1. 如果配置来源分散，模型与工具行为会难以维护。
2. 如果运行态与业务配置边界不清，后续迁移会变得危险。
3. 如果审计不控制敏感信息，系统将失去本地优先产品的可信度。

## 11. 验收标准

1. SQLite 能同时承载业务配置和运行态数据，但语义边界清晰。
2. 凭据不会以明文形式保存。
3. 会话、消息、调用和关键状态可以持久化并重新读取。
4. 审计记录能支持问题追踪，但不会默认泄漏敏感内容。
