# 工具、MCP 与 Skills 需求

## 1. 目标

系统应通过统一 Tool Registry 管理所有可调用能力，使聊天流程、TUI、API 和 Agent Runtime 面对的是统一能力视图，而不是多套来源各异的执行入口。

## 2. 范围与边界

本模块负责：

1. Tool Registry
2. 内置工具
3. MCP servers 及其工具发现
4. Skills 的发现与能力暴露
5. 工具元数据、启用状态和权限语义

本模块不直接负责：

1. 具体 UI 布局形态。
2. Agent 状态机编排。
3. 长期记忆策略。

## 3. Tool Registry 需求

系统应为每个工具维护统一元数据，包括：

1. 名称与显示名称。
2. 描述。
3. 来源类型。
4. 来源标识。
5. 输入参数 schema。
6. 输出说明。
7. 权限需求。
8. 是否启用。
9. 是否为核心能力。

Tool Registry 应支持注册、列出、查询、启用、禁用和执行入口复用。

## 4. 内置工具需求

系统应支持一组内置工具作为工作台基础能力。

内置工具应遵循与其他工具一致的注册、权限、审计和状态规则，不得绕过统一工具边界。

## 5. MCP 需求

系统应支持：

1. MCP server 配置管理。
2. MCP server 状态检查。
3. MCP server 工具发现。
4. MCP 工具向统一 Tool Registry 转换。
5. MCP 调用日志和错误分类。

MCP 相关工具应以统一工具元数据形式暴露，而不是由调用方直接面对协议细节。

## 6. Skills 需求

系统应支持：

1. 本地 Skills 发现。
2. Skill 基础说明读取。
3. Skill 启用与禁用。
4. 可执行 Skill 能力向 Tool Registry 暴露。

Skills 不应绕过 Tool Registry 和权限策略直接执行高风险操作。

## 7. 权限需求

每个工具应声明权限需求。权限范围至少应覆盖：

1. 只读访问。
2. 网络访问。
3. 文件读取。
4. 文件写入。
5. 命令执行。
6. 外部服务调用。
7. 记忆写入。
8. 高风险本地操作。

系统应支持 `allow / deny / ask` 三类策略结果。

## 8. 调用与审计边界

工具执行入口应统一负责：

1. 参数校验。
2. 权限判断。
3. 超时控制。
4. 审计记录。
5. 错误归一化。

聊天流程和 Agent Runtime 应通过统一执行入口调用工具，而不是直接调用任意函数。

## 9. 高风险操作控制

当工具涉及高风险权限时，系统应支持以下行为：

1. 拒绝执行。
2. 请求用户确认。
3. 记录权限决策与结果。

## 10. 约束与风险

1. 如果 MCP、Skills 和内置工具维持三套独立调用链，后续 Agent Runtime 会失控。
2. 如果工具元数据不统一，TUI、Web 和 API 无法给出一致状态视图。
3. 如果高风险工具绕过权限判断，审计和安全边界将失效。

## 11. 验收标准

1. 系统可以列出已注册工具及其来源与权限需求。
2. MCP 工具和 Skill 派生能力可以进入统一 Tool Registry。
3. 高风险权限可以被标记为需要确认或直接拒绝。
4. 工具调用会生成统一审计记录。
