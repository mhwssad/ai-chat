# Storage, Config And Audit Requirements

## 1. 目标

存储、配置和审计模块用于保证系统行为可理解、可恢复、可追踪。

配置文件负责显式系统配置，SQLite 负责运行态数据，审计日志负责记录关键行为。

## 2. 配置文件

### 2.1 配置内容

配置文件应管理供应商、模型、默认模型、MCP server、skills 启用策略、安全策略和基础系统设置。

### 2.2 API Key

配置文件不应保存明文 API Key。配置中应引用环境变量名或本地安全存储标识。

### 2.3 配置校验

系统应校验配置文件格式、必填字段、重复标识、默认模型是否存在、启用供应商是否具备必要凭据。

### 2.4 配置来源

MVP 中配置文件是 source of truth。Web 和 CLI 可以读取、展示和校验配置，但不要求写回配置。

## 3. SQLite 运行态数据

### 3.1 数据范围

SQLite 应保存会话、消息、模型调用记录、工具调用日志、权限决策、记忆索引和系统运行状态。

### 3.2 会话与消息

会话和消息应支持历史查看、继续对话、错误状态保存和模型使用记录。

### 3.3 调用记录

模型调用和工具调用应记录时间、来源、输入摘要、输出摘要、耗时、状态和错误。

### 3.4 迁移

数据库 schema 应支持版本化迁移。后续新增字段不应破坏已有会话数据。

## 4. 审计日志

### 4.1 审计范围

审计日志应覆盖模型调用、工具调用、MCP 调用、skills 调用、权限决策、记忆写入、配置检查和关键错误。

### 4.2 审计字段

审计记录至少包含时间、事件类型、来源模块、目标能力、输入摘要、输出摘要、状态、耗时、权限决策和错误信息。

### 4.3 隐私处理

审计日志不应无条件保存完整敏感输入。对于 API Key、密钥、文件内容和长文本，应使用摘要、脱敏或引用方式记录。

## 5. 数据边界

配置数据和运行态数据应分离。配置文件描述用户希望系统如何运行，SQLite 记录系统实际发生了什么。

这条边界应在 Web、CLI 和核心服务中保持一致。

## 6. 备份与可迁移

本地数据应尽量使用可备份、可迁移的结构。配置文件天然可复制，SQLite 数据应通过 schema 和导出能力支持后续迁移。

## 7. 验收标准

- 配置文件可以被读取和校验。
- 缺失 API Key 环境变量时能给出清晰错误。
- 会话和消息能保存到 SQLite 并重新加载。
- 模型调用和工具调用能生成审计记录。
- 审计日志不会保存明文 API Key。
- 配置数据和运行态数据不会混写。
