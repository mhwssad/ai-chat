# Agent Runtime 需求

## 1. 目标

系统应提供统一、可观察、可扩展的 Agent Runtime，使任务执行建立在共享模型、上下文、工具、记忆、RAG、权限和审计边界之上，而不是复制第二套运行逻辑。

## 2. 范围与边界

Agent Runtime 负责：

1. 接收任务输入。
2. 执行多轮推理与工具调用循环。
3. 维护任务状态。
4. 支持取消、错误处理和后续恢复演进。
5. 生成可观察的执行轨迹。

Agent Runtime 不应绕过：

1. ContextService
2. Tool Registry
3. 权限策略
4. 审计边界

## 3. 任务输入与执行模型

系统应支持以下 Agent 输入要素：

1. 会话标识。
2. 用户任务描述。
3. 最大迭代次数。
4. 可用工具范围。
5. 超时约束。

Agent 应基于上下文、可用工具和模型能力完成多轮执行，而不是只做单轮消息生成。

## 4. 执行状态机

Agent 执行应具有清晰状态，包括：

1. 待开始。
2. 运行中。
3. 等待用户确认。
4. 已取消。
5. 失败。
6. 成功。
7. 部分成功。

系统应能在 TUI、Web 或 API 中展示这些状态。

## 5. 工具调用与确认机制

Agent 的所有工具调用应经过统一工具执行入口。

当调用高风险工具时，系统应支持：

1. 直接拒绝。
2. 请求用户确认。
3. 将确认结果纳入后续执行策略和审计日志。

## 6. 记忆与 RAG 在 Agent 中的作用

Agent Runtime 应能使用：

1. 会话上下文。
2. 记忆结果。
3. RAG 上下文。
4. 工具执行结果。

但这些增强能力应通过统一上下文构建与检索边界进入执行流程。

## 7. 调试视图与可观察性

系统应提供可观察性输出，至少包括：

1. 当前任务输入。
2. 模型与配置选择。
3. 迭代次数。
4. 工具调用列表。
5. 错误与异常信息。
6. 最终结果摘要。

在后续阶段，系统应继续增强到更完整的 Agent Lab 视图。

## 8. 后台任务与恢复演进

当前阶段系统应至少支持取消和错误结束。

后续阶段系统应逐步支持：

1. 后台任务状态查询。
2. checkpoint 恢复。
3. 更强的长任务管理。

## 9. 约束与风险

1. 如果 Agent Runtime 复制聊天或工具逻辑，系统边界会失控。
2. 如果状态机不明确，长任务和错误恢复无法稳定演进。
3. 如果工具调用不进入统一权限和审计边界，高风险能力不可控。

## 10. 验收方向

1. Agent 可以完成至少一个需要工具调用的多步骤任务。
2. Agent 可以被取消并返回明确状态。
3. Agent 结果中可以查看状态、迭代次数和工具调用摘要。
4. 高风险工具调用具备确认或拒绝边界。
