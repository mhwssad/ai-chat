# 项目需求基线重组设计

## 背景

当前仓库已经在 `cs/requirements/` 下积累了一组需求文档，包括：

- `ai-workbench-requirements.md`
- `01-mvp-scope.md`
- `02-chat-and-models.md`
- `03-tools-mcp-skills.md`
- `04-memory.md`
- `05-web-and-cli.md`
- `06-storage-config-and-audit.md`
- `07-agent-runtime-roadmap.md`
- `data-model.md`

这些文档已经覆盖了产品定位、MVP 范围、聊天、工具、记忆、交互入口、存储审计、Agent 路线图和数据模型等主题，但存在以下问题：

1. 文档结构以历史专题为主，缺少统一总纲和稳定的信息架构。
2. 多份文档之间存在重复描述，例如 MVP、CLI、阶段计划、模块边界。
3. 一部分内容仍保留旧阶段假设，与当前项目方向不一致，例如独立业务 CLI 假设。
4. 功能需求、架构边界、数据模型和路线图混写在不同文档中，阅读成本高。
5. 现有文档更像逐步积累的说明集合，而不是正式的项目需求基线。

本次设计目标是重组整个 `cs/requirements/` 文档集，使其成为面向协作者和开发者都可使用的统一需求基线。

## 目标

### 主要目标

1. 将现有需求文档重组为一套统一、清晰、稳定的项目需求基线。
2. 新需求基线同时服务于产品协作和开发实现，不只面向单一受众。
3. 以目标产品为准组织需求，而不是被当前代码实现完全绑定。
4. 保留阶段性路线图，明确 `MVP / 近期 / 远期` 的范围和演进顺序。
5. 使用“业务能力 + 系统层次”混合结构，让文档既能按功能阅读，也能按架构边界理解。
6. 同步修正文档中与当前方向明显冲突的内容，例如独立业务 CLI 假设。

### 非目标

1. 不在本次工作中重写业务代码或同步推进功能开发。
2. 不把需求文档写成当前实现的逐文件注释。
3. 不要求所有需求都立即与当前代码完全一致。
4. 不在本次工作中设计团队协作、多用户、云同步等超出当前项目边界的能力。

## 设计原则

### 1. 目标产品优先

新需求基线以目标系统为准。当前实现可作为约束和校正依据，但不会成为需求结构本身的主导来源。

### 2. 当前方向校正

凡是当前项目方向已经明确改变的内容，文档必须同步调整。例如：

- `main.py` 命令入口收敛为 `serve` 与 `tui`
- 用户交互入口应以 `Web / TUI / API` 为主，而不是保留旧的独立业务 CLI 假设

### 3. 单文档单主问题

每份文档应回答一个主问题，避免跨文档重复维护同一组需求。例如：

- 聊天与模型只在聊天模型文档中展开
- 工具、MCP、skills 只在能力系统文档中展开
- DI、组合根、共享服务层次只在架构文档中集中说明

### 4. 路线图集中管理

`MVP / 近期 / 远期` 的阶段性内容集中在路线图文档中维护。其他专题文档可以引用阶段，但不再各自维护完整阶段计划。

### 5. 中文为主，关键术语保留英文

文档整体使用中文叙述，关键术语保留英文，例如：

- Current Baseline
- Target State
- Web / TUI / API
- Agent Runtime
- Tool Registry
- Dependency Injection

### 6. 面向协作者与开发者双重可读

文档既要能让协作者快速理解项目目标、用户场景和能力范围，也要能让开发者明确模块边界、系统层次和数据约束。

### 旧文档处理方式

重组完成后，旧文档不再继续作为正式需求基线维护。处理策略如下：

1. 使用新的文件名与编号体系替换原有结构。
2. 原有文档内容不是简单复制，而是基于新结构重写。
3. 如需保留历史痕迹，应通过 Git 历史而不是继续保留平行版本。

## 写作口径

所有新文档统一采用以下写法：

1. 先写 `目标`
2. 再写 `范围与边界`
3. 再写 `核心需求`
4. 再写 `约束 / 风险 / 审计 / 安全`
5. 最后写 `验收标准`

统一语言规则如下：

- 需求语句以“系统应……”为主
- 避免写成实现过程说明
- 避免按代码文件顺序描述需求
- 非架构类文档不大量写类名和具体文件路径
- 架构文档与数据模型文档可以适度引用当前实现术语，用于说明边界

## 与当前项目方向的对齐要求

重组后的需求基线必须反映以下方向：

1. 项目定位是本地优先的 AI 工作台与 Agent 能力平台。
2. 交互入口应围绕 `Web / TUI / API` 展开。
3. 业务交互型命令行能力已收敛到 TUI，不再把独立业务 CLI 作为正式产品入口。
4. 存储、模型、工具、记忆、审计等能力应通过共享核心服务组织，而不是在入口层重复实现。
5. 阶段规划必须服务于整体平台演进，而不是停留在单一聊天页面视角。

## 验收标准

重组工作完成时，应满足以下标准：

1. `cs/requirements/` 形成一套统一编号和命名规则的新文档集。
2. 协作者只阅读 `00 + 01` 即可理解项目定位、范围和阶段目标。
3. 开发者阅读 `02 ~ 09` 即可理解主要能力边界、系统层次和数据约束。
4. 文档中不再保留独立业务 CLI 作为正式产品入口的旧假设。
5. 阶段路线图集中管理，不再在多个专题文档中各自维护不同版本。
6. 同一主题只在一个主文档中完整展开，交叉重复显著减少。
7. 数据模型、存储策略、工具边界、Agent 演进方向之间术语一致。

## 风险与注意事项

1. 如果只是复制旧文档并改名，结构问题和重复问题不会真正解决。
2. 如果过度依赖当前代码实现，新需求基线会失去目标产品文档的作用。
3. 如果完全脱离当前项目方向，例如继续保留旧 CLI 假设，需求文档会再次失真。
4. 如果阶段性内容分散在多个专题文档中，后续维护会迅速失控。
