# MVP Implementation Plan

## 1. 目标

本计划把 AI Workbench 的 MVP 需求拆成可执行实施阶段。MVP 的核心目标是先交付一个可靠的本地 AI 工作台底座：Web 可聊天、CLI 可诊断、多供应商模型可配置、会话可持久化、调用可审计，并为工具、MCP、skills、记忆和 Agent Runtime 留好边界。

本计划不覆盖第二、三阶段的完整 Agent 编排、后台任务队列、长期记忆自动提取、项目知识库和完整沙箱。

## 2. 实施原则

- 先搭核心服务，再接 Web 和 CLI。
- Web 与 CLI 必须共享同一套异步核心。
- 配置文件负责系统显式配置，SQLite 负责运行态数据。
- 所有模型调用、聊天流程、工具执行入口和存储访问优先使用异步接口。
- 每个阶段都应有可验证产物，不把风险堆到最后。
- 工具、MCP、skills 先建立统一注册表边界，不在 MVP 阶段追求完整管理平台。

## 3. 阶段 0：基线整理

### 3.1 目标

确认当前项目结构、已有聊天能力、已有配置方式、数据库状态和测试入口，为后续改造建立安全基线。

### 3.2 任务

- 梳理现有目录结构和模块职责。
- 确认 Web 服务入口、CLI 入口和当前聊天调用链。
- 确认现有配置文件、环境变量和模型供应商实现。
- 确认当前数据存储方式和迁移机制。
- 记录当前可运行命令和测试命令。

### 3.3 验收

- 能说明当前聊天请求从入口到模型调用的路径。
- 能说明当前会话和消息是否已持久化。
- 能说明哪些代码可复用，哪些需要重构。

## 4. 阶段 1：配置与模型核心

### 4.1 目标

建立多供应商和模型管理的核心抽象，使聊天流程不直接依赖具体供应商。

### 4.2 任务

- 定义供应商配置结构。
- 定义模型配置结构。
- 实现配置读取和校验。
- 实现模型列表聚合。
- 实现默认模型解析。
- 实现统一模型调用接口。
- 为供应商错误建立统一错误类型。

### 4.3 验收

- 可以从配置文件读取供应商和模型。
- 可以列出启用模型。
- 缺少 API Key 环境变量时有明确错误。
- 至少一个供应商可以通过统一接口完成聊天调用。
- 新增供应商不需要修改 Web 聊天主流程。

## 5. 阶段 2：SQLite 运行态存储

### 5.1 目标

建立 MVP 所需的运行态存储，支持会话、消息、模型调用记录、工具调用记录和审计日志。

### 5.2 任务

- 定义数据库初始化流程。
- 定义会话表。
- 定义消息表。
- 定义模型调用记录表。
- 定义工具调用记录表。
- 定义审计日志表。
- 建立基础迁移策略。
- 提供异步存储接口。

### 5.3 验收

- 可以创建会话并保存消息。
- 可以重新加载历史会话。
- 可以记录模型调用状态和错误。
- 数据库 schema 有版本边界。
- Web 和 CLI 不直接操作数据库细节。

## 6. 阶段 3：聊天核心服务

### 6.1 目标

建立 Web 和 CLI 共享的聊天核心服务，支持会话、消息、上下文组装、模型调用和流式输出。

### 6.2 任务

- 实现创建会话。
- 实现发送用户消息。
- 实现上下文组装。
- 实现模型调用。
- 实现流式响应事件。
- 实现消息状态更新。
- 实现取消接口预留。
- 实现会话内记忆的基础上下文来源。

### 6.3 验收

- 聊天核心可以在不依赖 Web 的情况下被调用。
- 一次聊天会保存用户消息和助手消息。
- 流式响应可以逐步产出内容。
- 模型调用失败时会保存错误状态。
- 模型切换只影响后续消息。

## 7. 阶段 4：Web MVP

### 7.1 目标

完成第一阶段主要用户入口，让用户可以在 Web 中完成稳定聊天。

### 7.2 任务

- 接入聊天核心服务。
- 实现会话列表。
- 实现聊天消息展示。
- 实现流式输出展示。
- 实现模型选择。
- 实现错误展示。
- 实现基础供应商状态展示。
- 预留高级模式或 Agent 实验室入口。

### 7.3 验收

- 用户可以创建会话并发送消息。
- 用户可以看到流式回复。
- 用户可以切换模型。
- 页面刷新后可以继续历史会话。
- 供应商或模型错误能在界面中清晰展示。

## 8. 阶段 5：CLI MVP

### 8.1 目标

完成开发者最小入口，用于启动、诊断和一次性聊天请求。

### 8.2 任务

- 实现启动服务命令。
- 实现一次性聊天命令。
- 实现模型列表命令。
- 实现供应商状态命令。
- 实现配置检查命令。
- 实现工具列表命令。

### 8.3 验收

- CLI 可以发起一次聊天请求。
- CLI 可以指定模型。
- CLI 可以列出模型和供应商。
- CLI 可以检查配置问题。
- CLI 与 Web 使用同一套核心服务和配置解析。

## 9. 阶段 6：工具注册表与权限边界

### 9.1 目标

建立统一工具注册表的 MVP 能力，为后续 MCP、skills 和 Agent Runtime 做准备。

### 9.2 任务

- 定义工具元数据结构。
- 实现工具注册表。
- 支持工具列出、启用、禁用和状态展示。
- 定义权限声明结构。
- 实现基础权限策略。
- 实现统一工具执行入口。
- 提供至少一个低风险示例工具用于验证流程。

### 9.3 验收

- 系统可以列出工具。
- 工具可以声明来源和权限。
- 工具调用经过统一执行入口。
- 高风险权限可以被标记为拒绝或需要询问。
- 工具调用可以写入审计日志。

## 10. 阶段 7：审计、错误与可观察性

### 10.1 目标

让 MVP 的关键行为可追踪、可诊断、可恢复。

### 10.2 任务

- 统一模型调用错误。
- 统一工具调用错误。
- 记录模型调用审计日志。
- 记录工具调用审计日志。
- 记录权限决策。
- 在 Web 和 CLI 中展示用户可理解错误。
- 避免在日志中保存明文 API Key 和敏感内容。

### 10.3 验收

- 模型认证失败、限流、网络错误可以区分。
- 工具执行失败可以记录来源和错误。
- 审计日志包含时间、来源、状态、耗时和错误摘要。
- 敏感信息不会以明文进入日志。

## 11. 阶段 8：MVP 验收与收口

### 11.1 目标

确认 MVP 满足需求文档中的第一阶段范围，避免遗漏核心能力。

### 11.2 任务

- 按需求文档执行验收清单。
- 补齐关键测试。
- 补齐开发者说明。
- 检查 Web 和 CLI 行为一致性。
- 检查配置、存储和审计边界。
- 标记第二阶段待办。

### 11.3 验收

- Web 完成一次完整流式聊天。
- CLI 完成一次聊天请求。
- 至少两个模型可被列出和选择。
- 会话历史可保存和加载。
- 配置错误可诊断。
- 工具注册表可列出工具。
- 审计日志可记录模型调用和工具调用。

## 12. 推荐实现顺序

1. 阶段 0：基线整理。
2. 阶段 1：配置与模型核心。
3. 阶段 2：SQLite 运行态存储。
4. 阶段 3：聊天核心服务。
5. 阶段 4：Web MVP。
6. 阶段 5：CLI MVP。
7. 阶段 6：工具注册表与权限边界。
8. 阶段 7：审计、错误与可观察性。
9. 阶段 8：MVP 验收与收口。

## 13. 并行机会

- 配置与模型核心可以和数据模型文档并行推进。
- Web UI 接入可以在聊天核心接口稳定后开始。
- CLI 命令可以在核心服务完成后与 Web 接入并行。
- 工具注册表可以在聊天核心稳定后独立推进。
- 审计日志应尽早接入存储，不应等到最后一次性补。

## 14. 主要风险

- 过早实现完整 Agent Runtime 会拖慢 MVP。
- Web 和 CLI 分别实现逻辑会导致后续维护困难。
- 没有统一错误结构会让用户难以判断问题来源。
- 没有审计边界会让工具、MCP 和 skills 的安全风险失控。
- 配置文件和 SQLite 职责混乱会导致数据迁移困难。
